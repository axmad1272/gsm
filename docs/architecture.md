# Архитектура GSM

## Стек

- **Backend:** Python 3.13, FastAPI, SQLAlchemy 2, PostgreSQL 16, Alembic.
- **Фоновые задачи:** очередь в Postgres (`SELECT … FOR UPDATE SKIP LOCKED`). Отдельный брокер пока не
  нужен; воркеры масштабируются горизонтально.
- **PDF:** reportlab + qrcode. Файлы — через интерфейс `FileStorage` (локально, в проде — S3/MinIO).
- **Frontend:** будет отдельным приложением (React) поверх этого API.

## Как устроен код

```
backend/app/
  core/            конфиг, БД, права, аутентификация, идемпотентность, хранилище
  modules/
    shipments/     модуль «Расход»: модели, расчёт количества, сервис ЖЦ, чтение, PDF, API
    didox/         граница с Didox (gateway), правила подбора оснований, контрагенты, очередь сверки
    warehouses/    склады, пользователи, доступ к складам
    periods/       закрытые месяцы
    audit/         журнал действий
  worker.py        фоновая сверка ручных оснований с Didox
```

Каждый модуль — свои модели, сервис и API. Новые модули («Приход», «Сверка 1С», «Технолог»)
добавляются рядом и не трогают существующие.

## Ключевые решения

| Требование | Как сделано |
|---|---|
| Права на сервере | `Actor.require(permission)` и `require_warehouse()` в каждом методе сервиса. Роль — набор прав по умолчанию, у пользователя можно добавить или убрать отдельные права. |
| Точность количества | Объём в мл, масса в граммах (`BIGINT`), плотность — `NUMERIC(6,4)`. мл × кг/л = г, без промежуточного округления. Режим ввода — настройка склада. |
| ID / номер / редакция / PDF | `shipments.id`, `number` (+ склад, год), `shipment_revisions`, `shipment_prints.id`. |
| Резерв и освобождение номера | `number_sequences` с блокировкой строки; номер удалённой ненапечатанной ТТН попадает в `released_numbers` и выдаётся первым. Уникальный индекс по номеру среди неудалённых ТТН. |
| Нет двойного расхода | Движение проводится только при переходе `created → issued` под блокировкой строки ТТН. Уникальный частичный индекс: одна проводка на редакцию, склад и направление. Перепечатка движений не создаёт. |
| Исправление после печати | Новая редакция, причина, изменённые поля. Если менялись склад, дата, операция или количество — сторно прежних движений и новые движения. Иначе (например, госномер) движения не трогаются. |
| Повторный клик и сетевой сбой | Заголовок `Idempotency-Key`: повтор возвращает сохранённый результат. Неуспешная операция ключ не занимает. |
| QR | Указывает на конкретный выпуск PDF: `GET /api/verify/prints/{print_id}` → `current`, `superseded`, `outdated_revision`, `annulled`. |
| Проверки по редакции | `shipment_reviews.revision_no`. Решение по прежней редакции показывается как `stale` и не считается. |
| Didox | Весь внешний API — за интерфейсом `DidoxGateway`. Правила подбора — чистые функции, одинаковые для формы и повторной проверки на сервере. |
| Ручной режим | Только при разрешении склада и праве `didox.manual_basis`. Помечается `manual_pending` и ставится в очередь сверки. Источник «ручной» после сверки не переписывается. |
| Закрытый месяц | `ensure_open()` проверяет все затронутые даты: прежнюю и новую дату отгрузки и даты сторнируемых движений. |
| Статус по осям | API отдаёт `status.document`, `status.didox`, `status.onec`, `status.review`, `status.period`, `status.closed`. |
| Персональные данные | ПИНФЛ водителя и ID владельца транспорта скрываются без `shipment.view_personal`, в том числе в истории редакций. |

## Решения, которые стоит подтвердить

1. **Закрытие ТТН** — явное действие (право `shipment.close` у бухгалтера и финансиста) после двух
   положительных проверок текущей редакции и при отсутствии требования перепечатки.
2. **Закрытая ТТН** оператором не исправляется. Административное исправление снимает закрытие,
   и проверки нужно пройти заново.
3. **Сторно** датируется датой исходного движения. Поэтому исправление ТТН из закрытого месяца
   блокируется.
4. **Повторный запрос в Didox** при исправлении делается, только если изменились контрагент, дата или
   выбранные документы. Иначе используются сохранённые статусы, и правка госномера не зависит от
   доступности Didox.
5. **Видимость перемещений:** ТТН перемещения видна и складу-отправителю, и складу-получателю.

## Статус реализации

Готово (этап 1, с тестами):

- ЖЦ ТТН: черновик → создана → напечатана → исправлена → перепечатана → проверена → закрыта,
  удаление и аннулирование;
- нумерация по складу и году с резервом и освобождением;
- движения топлива со сторно, остаток по складу;
- лимит исправлений, возврат попытки замечанием, административное исправление;
- PDF, хранение выпусков, проверка по QR;
- подбор и серверная проверка оснований Didox, «подтверждён доверенностью», ручной режим
  и фоновая сверка;
- права, доступ к складам, скрытие персональных данных, закрытые месяцы, аудит;
- реестр, черновики, очередь проверки, история и поиск с явными фильтрами.

Следующие этапы:

1. **Реальный клиент Didox** (`HttpDidoxGateway`) — нужны документация API, тестовый аккаунт и текущий
   `didox_glue.py`.
2. **Сверка с 1С** — импорт Excel «Реализация» и «Перемещение», кандидаты, подтверждения и отказы,
   группы N:M, защита от повторного импорта.
3. **Аутентификация** — SSO/JWT вместо dev-заголовка `X-User-Id`.
4. **Frontend** на новой дизайн-системе.
5. **Миграция данных** из текущей системы (ID, номера, редакции, PDF, движения, связи 1С, аудит).
6. Печатная форма ТТН по утверждённому макету.
